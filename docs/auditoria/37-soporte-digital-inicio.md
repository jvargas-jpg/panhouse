# Soporte Digital → Inicio — auditoría, correcciones y validación

28 de octubre de 2026. Alcance: únicamente Inicio de Soporte Digital. La implementación (helper, ruta, DTOs, página, CSS) ya existía sin commit en el árbol de trabajo al iniciar esta tarea — construida en una sesión/máquina anterior. Este trabajo fue auditarla contra el master prompt, corregir lo que no cumplía, y añadir la cobertura de tests y QA que faltaba.

| Punto | Tema | Resultado |
|---|---|---|
| A | Estado previo | `SoporteDigitalHomePage.tsx`, `server/helpers/soporteDigitalHome.ts`, `server/routes/soporteDigitalHome.routes.ts` y `shared/soporteDigitalHome.ts` ya existían sin commit, registrados en `app.ts`/`HomePage.tsx`/`AppLayout.tsx`. No había ningún test (backend ni frontend) ni evidencia de QA visual. |
| B | Rol técnico | `soporte_digital`, ya presente en `ROLES` (enums.ts). Ruta `GET /api/soporte-digital/inicio` con `requireAuth` + `requireRole('soporte_digital')`. |
| C | Dominio reutilizado | Sin tablas nuevas. Reutiliza `work_items` (`tipo='soporte_digital'`), `proyectos`, `fichas_trazabilidad` (`soporte_digital_fecha_activacion`, `soporte_digital_fecha_envio_formulario`, `digital_estatus`) y `ficha_documental_datos` (secciones `diseno`.`paqueteFinalCargado` y `digital`.`pruebaArchivos`/`cargaKdp`/`cargaKindle`) — confirmados contra `fichaDocumentalCatalogo.ts`, ningún campo inventado. |
| D | Origen real del work item | Única fuente actual: `habilitarActivacionAmazon` (businessKey `activacion_amazon`), disparada en paralelo a la primera validación de Calidad (F7) — confirma que Soporte Digital puede activarse antes del paquete final, tal como exige el master prompt. | E | Amazon/KDP | Sin API, OAuth, scraping ni webhook de Amazon en el código. Verificado que el texto del dashboard nunca implica sincronización automática. |
| F | Credenciales | No se almacena ni se muestra cuenta, contraseña ni 2FA de Amazon en ningún punto de Inicio. |
| G | **Bug real #1 (corregido)** | `digital_estatus='Completado'` hacía que el *summary* (agregado por proyecto, usa `stage(r)` crudo) contara el proyecto como `completed`, pero la fila de tarea (`toTask`) mostraba fijo `stage:'preparation'` para cualquier fila cuyo `business_key` fuera `activacion_amazon` — rompía la regla de una sola fuente de verdad (§37 del master prompt: card y flow deben coincidir con la fila). Corregido: `stage` de la tarea ahora respeta `internalDone` antes que el tipo de fila. |
| H | **Bug real #2 (corregido)** | Más grave: como hoy solo existe un work item real por proyecto (el de activación), el código usaba `business_key==='activacion_amazon'` como proxy de "cuenta aún no activada" — válido en el momento de creación, pero esa misma fila persiste después de activarse la cuenta. Resultado: aun con paquete final disponible, cuenta activada y archivo cargado, la etiqueta de tarea quedaba congelada en "Enviar/Registrar la activación Amazon" para siempre, y `waitingPackage` nunca se activaba para la fila real. Corregido: se reemplazó el proxy por la señal real (`fichasTrazabilidad.soporteDigitalFechaActivacion`, columna `activation` del SQL) para decidir `waitingPackage` y el label de respaldo; `stage` pasó a usar siempre `stage(r)` (con el override de completado). Verificado con test dedicado y QA visual (fila "Ciudad de Papel", vencida, en etapa "Para pruebas KDP" con label "Revisar los archivos finales para KDP"). |
| I | Gates | `gate_bloqueante`/`estado='bloqueado'` de `work_items` se respeta tal cual existe; sin inventar un gate nuevo. El texto mostrado para un bloqueo de solvencia (`/solvencia\|financ\|cobranza/i`) es genérico ("Bloqueado por solvencia"), sin montos, saldo ni factura — verificado con test y QA (`JSON.stringify` del dashboard no contiene esos términos). |
| J | Activación temprana vs. publicación | Confirmado en código y QA: un proyecto puede estar en "En preparación" mientras Calidad/Diseño siguen activos; "Para pruebas KDP" exige explícitamente paquete final **y** cuenta activada; "Cargas registradas" exige fecha real de carga KDP/Kindle; "Digital completado" es un estatus macro explícito, nunca inferido de la sola existencia de un archivo. |
| K | Dashboard endpoint | `GET /api/soporte-digital/inicio`, sin query params admitidos (`z.object({}).strict()`, 400 si llegan). Dos queries (`Promise.allSettled`), sin N+1, sin llamadas a Drive ni a Amazon. |
| L | Summary DTO | `{ preparation, testing, loaded, completed }`, agregado por proyecto (no por fila) para las cuatro cards superiores. |
| M | Priority task DTO | `workItemId, projectId, projectTitle, projectCode, authors, coverUrl, stage, taskType, taskLabel, deadline, deadlineState, status, blocker, actionable, packageAvailable, href` — una fila por *work item*, nunca por proyecto (verificado con un proyecto de dos tareas digitales). |
